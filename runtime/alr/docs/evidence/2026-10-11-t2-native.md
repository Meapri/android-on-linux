# T2 — Termux 네이티브 대비 CLI 성능

- **날짜**: 2026-10-11
- **엔진 라벨**: `engine=alr`
- **기기**: Samsung SM-S937N, Snapdragon 8 Elite SM8750, Android 17 (SDK 37)
- **컨텍스트**: `uid=10057  u:r:untrusted_app_27:s0  Seccomp=2` (Termux sshd를 거친 셸)
- **게스트**: Ubuntu 26.04.1 LTS (glibc 2.43), uutils coreutils
- **하네스**: [`tests/device/t2_native.sh`](../../tests/device/t2_native.sh), hyperfine 2.0.0 `-N`, 워밍업 3회, 중앙값. 원본 출력은 [2026-10-11-t2-native.txt](2026-10-11-t2-native.txt)다.
- **목적**: [ADR 0005](https://github.com/Meapri/android-on-linux/blob/main/docs/adr/0005-termux-first-goals.md) T2, 워크로드마다 `alr / 네이티브 <= 1.2`

## 읽는 법

- **같은 바이너리 비교가 아니다.** glibc 게스트 바이너리는 alr 밖에서 실행할 수 없으므로, 네이티브 쪽은 Termux 패키지의 같은 프로그램이다. node가 0.41배인 것은 alr이 빨라서가 아니다. Termux의 node 빌드가 이 기기에서 공식 빌드보다 느리기 때문이다.
- **`alr run` 한 번에는 고정 비용이 붙는다.** `alr config`(9.1 ms)와 `alr run /bin/true`(14.6 ms)의 차이가 약 5.5 ms다. 기기용 계측 빌드로 나눠 보면 다음과 같다(`/bin/true`, 3회).
  - 슈퍼바이저 시작 전 준비: 0.5~0.75 ms (resolver 스레드 기동 0.15~0.25 ms 포함)
  - fork부터 첫 정지까지: 0.6~1.1 ms
  - ld.so exec까지: 1.3~2.1 ms
  - glibc 초기화와 첫 SIGSYS까지: 약 0.45 ms
  - 종료와 정리: 약 0.6 ms

  게스트 셸 안에서 연달아 실행하는 경우(`x20` 행)에는 이 비용이 대부분 사라진다.
- **apt는 데이터 크기가 다르다.** Ubuntu의 패키지 목록은 144 MB, dpkg info는 31 MB다. Termux는 각각 1.9 MB와 3.8 MB다. apt와 dpkg의 일은 이 크기에 비례하므로 비율로 판정하지 않는다. 같은 실행에서 alr이 더한 일은 프로세스 30개, SIGSYS 구제 52건, 신호 전달 29건이다. 프로세스 하나의 실행 비용(게스트 셸 기준 약 1.8 ms)과 ptrace 왕복(약 60 µs)으로 어림하면 60 ms 안팎이다. 이 수치는 계산한 값이며, 따로 재지는 않았다.

## 한계

- Snapdragon 한 대에서만 쟀다. 이 기기는 짧은 측정에서 클럭 변동이 크다(같은 명령의 표준편차가 10~25%). 그래서 평균이 아니라 중앙값을 쓴다.
- T2의 공식 워크로드 가운데 apt는 공정한 비율을 얻을 방법이 아직 없다.
