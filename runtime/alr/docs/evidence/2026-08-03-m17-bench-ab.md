# M17 — `alr bench` A/B, 그리고 추정 4개 중 3개가 빗나간 이유

- **날짜**: 2026-08-03
- **기기**: MediaTek MT8775, Android 16, 커널 `6.1.145-android14`, `uid=10297 Seccomp=2`
- **하네스**: `tests/device/bench.sh` (`./scripts/dev-push.sh bench-ab`)

## 0. 왜 이게 남아 있었나

`docs/07-acceptance.md` §2 M8 의 두 줄이 `PENDING_DEVICE` 로 남아 있었고, 같은 문서 §4.4 가 이유를 정확히 적어 두었다:

> 막는 것은 기기가 아니라 하네스다 — 기기는 있고 `alr bench` 가 없다.

즉 기기 부족이 아니라 **우리가 안 만든 것**이 막고 있었다. 만들었다.

## 1. 결과

```
ALR BENCH NODE COLD vs PROOT:      6.60x  MEASURED  alr 55 / proot 363 ms
ALR BENCH EXEC THROUGHPUT:         351 exec/s  MEASURED  alr 351 / proot 135 exec/s
ALR MEDIATION INVARIANT:           PASS  path_traps=0 syscall_stops=0  MEASURED
```

`MEDIATION INVARIANT` 를 **50회 exec 루프 아래에서** 다시 확인한 것이 이번의 추가분이다. 이전에는 단일 명령에서만 봤다 — PRoot 와 갈리는 불변식이 부하 중에도 성립한다는 것이 요점이므로, 부하를 준 채로 보는 것이 맞다.

## 2. 측정 규칙 — 양쪽에 같은 바이너리

M8 의 `git status` 비교는 세 실행의 git 빌드가 달라(2.55/2.43/2.53) 약점이 있었고 문서가 그렇게 적어 두었다. `npm ci`(M12 §4)는 node·npm·락파일·npm 캐시를 복사해 그 문제를 없앴고, 이번에도 같은 규칙을 따랐다:

- **exec 프로브**: 세 줄짜리 C 파일을 게스트 gcc 로 **한 번** 컴파일해 proot rootfs 로 복사. 런타임 말고는 다를 것이 없다.
- **node**: M12 에서 이미 양쪽을 동일하게 맞춰 둔 것을 그대로 썼다.

타이머는 bash `EPOCHREALTIME` 이다. 처음에는 `/usr/bin/time -f %e` 를 썼는데 **Termux 호스트에 GNU time 이 없어** 모든 측정이 빈 값으로 나왔다 — 게스트에는 있지만 스톱워치는 호스트 쪽에 있어야 한다.

5회 중 **중앙값**을 쓴다. 폰에서는 스케줄러 딸꾹질 하나가 평균을 크게 흔든다.

## 3. 추정이 빗나갔다 — 그리고 방향이 한쪽이다

`docs/00-product.md` §4 의 "방어 가능한 주장" 표는 이제 이렇게 된다:

| 워크로드 | 추정 | 실측 |
|---|---|---|
| `git status` | 1.5–4× | **34.8×** |
| `npm ci` | 1.5–3× | **3.12×** (유일하게 맞음) |
| `node -e 0` 콜드 스타트 | **1.05–1.4×** | **6.60×** |

**4개 중 3개가 빗나갔고 전부 같은 방향이다** — 우리가 PRoot 의 syscall 당 비용을 과소평가했다. 특히 콜드 스타트는 문서가 "여기가 가장 약하다, 히어로 벤치로 쓰지 말 것" 이라고 못박아 둔 항목인데 6배가 넘게 나왔다.

### 그래도 히어로로 올리지 않는다

배수가 커진 이유는 **분자가 아니라 분모**다. `node -e 0` 의 alr 쪽 55 ms 는 대부분 V8 초기화이고 alr 이 기여하는 몫은 작다. proot 쪽 363 ms 가 큰 것이 배수를 만들었다.

즉 6.60× 는 "alr 이 node 를 빠르게 한다" 가 아니라 "proot 가 node 시작을 크게 느리게 한다" 는 진술이다. 히어로 벤치는 `git status` 와 `npm ci` 로 그대로 둔다.

같은 논리로, 표에 남은 추정("로그인/세션 진입 30–100 ms", "UnixBench 상한 1.8×")도 **실측 전까지 인용하지 않는다.** 세 번 빗나간 방법으로 만든 나머지 두 개를 신뢰할 이유가 없다.

## 4. exec 처리량 — RISKS R5 에 대한 부분 답

R5 는 "execve 마다 DSO 를 하나 더 매핑하는 alr 고유 비용이 히어로 벤치를 잡아먹는가" 였다.

alr 351 exec/s vs proot 135 exec/s — proot 대비로는 2.6배 여유가 있다. 다만 **이것이 R5 를 완전히 닫지는 않는다**: R5 의 진짜 질문은 proot 대비가 아니라 **native 대비** alr 이 얼마를 무는가이고, 이 하네스에는 native 다리가 없다.

없는 이유는 기술적이다 — 프로브는 게스트 glibc 바이너리이고 Termux 호스트는 bionic 이라 그대로는 안 돈다. M8 의 native 숫자(기동 24 ms vs alr 28 ms)가 현재 그 질문에 대한 유일한 근거이며, 거기서 alr 고유 비용은 exec 당 +4 ms 수준이다. **exec 처리량의 native 다리는 미측정으로 남긴다.**

## 5. 스펙과의 의도적 차이

`docs/06-cli-spec.md` §1 은 `alr bench` 를 CLI 서브커맨드로 적어 두었다. 여기서는 **기기 하네스**로 만들었다. 이유: 여기서 나오는 모든 숫자가 비교 대상으로 proot-distro 를 필요로 하는데, **측정 대상 런타임 안에서 다른 런타임을 오케스트레이션하는 것은 자리가 틀리다.** `tests/device/breadth.sh` 도 같은 이유로 셸 하네스이면서 수용 라인을 낸다.

조용히 다르게 만들지 않고 여기와 하네스 헤더 양쪽에 적어 둔다.
