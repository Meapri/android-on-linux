# M11 — 호환성 폭 96/96, 그리고 그것을 막고 있던 네 개의 결함

- **날짜**: 2026-08-02
- **기기**: MediaTek arm64, `uid=10297 Seccomp=2 u:r:untrusted_app_27:s0`
- **게스트**: Ubuntu 24.04.4 base arm64, glibc 2.39, 패치 없음
- **결과**: **MEASURED — 큐레이션된 96개 패키지 중 설치 96/96, 실행 95/96**

[07-acceptance.md §5](../07-acceptance.md) 가 요구하는 지표다. 포지셔닝이 "속도" 가 아니라 "Ubuntu 아카이브 전체를 무수정으로 쓴다" 이므로, 이 숫자가 grun 대비 유일한 차별점이다.

```
ALR BREADTH: install=96/96 run=95/96
```

실행 실패 1건은 `php-cli` 이며, **우리 인터포지션 탓이 아님이 증명되었다**(§5).

## 측정 방법 — 왜 이렇게 재는가

`tests/device/breadth.sh`.

- **설치와 실행을 분리해서 센다.** 설치는 되는데 실행이 안 되는 패키지는 통과가 아니다.
- **배치 설치는 속도용일 뿐, 귀속은 개별로 한다.** `dpkg-query` 로 패키지마다 상태를 확인하고, 배치가 실패하면 구성원을 하나씩 재시도한다. 패키지 하나가 나머지 아홉을 끌고 내려가면 안 된다.
- **실패는 추측한 분류가 아니라 실제 stderr 꼬리를 기록한다.**

## 1. 첫 측정이 96개 전부 실패로 나온 이유 — 측정 도구의 버그

첫 실행은 `install=12/96` 이었고, 그 12개는 **base rootfs 에 원래 있던 것들**이었다. 즉 **새로 설치된 것이 0개**였다.

원인은 alr 이 아니라 스크립트였다:

```sh
apt_install() { ... >/tmp/alr-breadth-apt.log 2>&1; }
```

Termux 호스트의 `/tmp` 는 `drwxrwx--x shell shell` 로, 앱 uid 는 쓸 수 없다:

```
$ echo x > /tmp/alr-probe
bash: /tmp/alr-probe: Permission denied
$ ls -ld /tmp
drwxrwx--x. 2 shell shell 40 /tmp
```

**리다이렉트가 실패하면 함수는 apt 를 실행하기도 전에 0이 아닌 값을 반환한다.** 그것이 하위에서 "96개 패키지 전부 설치 불가" 로 읽혔다. `$TMPDIR`(`$PREFIX/tmp`)로 바꿔 해결.

> 측정 도구가 조용히 고장 나면 그 결과는 제품에 대한 진술이 아니다. 0/96 같은 극단값은 제품보다 하네스를 먼저 의심해야 한다.

## 2. `ldconfig` — 하나가 무너지면 그 뒤가 전부 무너진다

두 번째 실행에서 모든 배치가 실패했고, apt 로그가 원인을 지목했다:

```
Setting up libc-bin (2.39-0ubuntu8.8) ...
/sbin/ldconfig.real: Can't create temporary cache file /etc/ld.so.cache~: Read-only file system
/sbin/ldconfig.real: Can't stat /lib/aarch64-linux-gnu: No such file or directory
dpkg: error processing package libc-bin (--configure): ... exit status 1
```

`ldconfig` 은 정적 링크라 `LD_PRELOAD` 가 닿지 않는다. 그래서 Android 루트를 걸어다니고, 읽기 전용 `/system/etc` 에 캐시를 쓰려다 실패한다. 우리는 이미 no-op 셰임으로 대체하고 있었지만 — **`libc-bin` 업그레이드가 그것을 되돌린다.**

그리고 그 실패는 `libc-bin` 을 half-configured 로 남기므로 **이후의 모든 `apt install` 이 연쇄적으로 죽는다.** 96개가 "설치 불가" 로 보인 진짜 이유다.

**수정**: `dpkg-divert` 등록. dpkg 자신이 향후 버전을 `.distrib` 에 쓰고 우리 no-op 을 건드리지 않게 한다.

### 2.1 첫 수정은 틀린 경로를 diverted 했다

`/sbin/ldconfig` 을 등록했는데 아무 효과가 없었다. 진단:

```
$ dpkg-divert --list | grep ldconfig
local diversion of /sbin/ldconfig to /sbin/ldconfig.distrib     ← 등록은 됨
$ grep ldconfig /var/lib/dpkg/info/libc-bin.list
/usr/sbin/ldconfig                                              ← dpkg 가 아는 경로
/usr/sbin/ldconfig.real
```

**Ubuntu 24.04 는 merged-`/usr` 시스템이다.** `/sbin` 은 `usr/sbin` 심링크이고 dpkg 가 추적하는 이름은 `/usr/sbin/ldconfig` 다. 우리가 등록한 경로는 dpkg 가 한 번도 건드리지 않는 이름이라 diversion 이 조용히 무의미했다.

증상이 그것을 정확히 보여줬다 — `.distrib` 에 우리 셰임(148바이트)이, 실제 경로에 진짜 래퍼가 있는 **뒤바뀐** 상태.

**검증 (실제 업그레이드로)**:

```
$ apt-get install -y --only-upgrade libc-bin
Unpacking libc-bin (2.39-0ubuntu8.8) over (2.39-0ubuntu8.7) ...
Setting up libc-bin (2.39-0ubuntu8.8) ...          ← 에러 없음
$ ls -l /usr/sbin/ldconfig /usr/sbin/ldconfig.distrib
148 /usr/sbin/ldconfig          ← 우리 셰임, 그대로
387 /usr/sbin/ldconfig.distrib  ← 진짜 래퍼, dpkg 가 여기로 씀
$ dpkg -l libc-bin
ii  libc-bin  2.39-0ubuntu8.8
```

## 3. tarball 이 배포하는 절대 심링크 — 첫 부팅부터 깨져 있었다

`ldconfig` 을 고치자 설치는 91/96 까지 올라갔고, 남은 실패가 전부 같은 문장을 냈다:

```
/usr/bin/ucf: 588: awk: not found
/var/lib/dpkg/info/locales.config: 377: awk: not found
```

`awk` 가 없다. 그런데 `mawk` 도 `gawk` 도 설치되어 있었다:

```
/etc/alternatives/awk -> ../../usr/bin/gawk    ← 상대. 게스트가 만든 것, 정상
/usr/bin/awk -> /etc/alternatives/awk          ← 절대. 날짜 2024-04-09 = tarball 산 것
```

[M10 §1](2026-08-02-m10-apt-install-git.md) 에서 게스트가 *런타임에* 만드는 심링크는 상대화했지만, **tar 가 이미지에서 복원하는 심링크는 preload 를 거치지 않는다.** ubuntu-base 는 그런 링크를 **20개** 배포하고, 그중 하나가 `/usr/bin/awk` 였다.

즉 `awk` 는 이 프로젝트의 **모든 rootfs 에서 첫 부팅부터 동작한 적이 없었다.** 드러나지 않은 이유는 그때까지 아무 워크로드도 `awk` 를 부르지 않았기 때문이다.

**수정**: 추출 직후 트리를 훑어 절대 타깃을 상대화한다(`relativize_tree()`). `/proc`·`/sys`·`/dev` 타깃은 §4 재작성 대상이 아니므로 절대 유지.

```
alr: absolute symlinks: 20 relativized, 0 failed
$ find $R -type l -lname '/*' | wc -l
0
$ alr run /usr/bin/awk --version
mawk 1.3.4 20240123
```

## 4. 로케일 — "ubuntu-base 는 로케일을 배포하지 않는다" 는 틀린 주석이었다

96/96 설치 후 실행 실패가 2건 남았고 그중 하나가 `tmux` 였다:

```
tmux: need UTF-8 locale (LC_CTYPE) but have ANSI_X3.4-1968
```

`alr.c` 에는 "ubuntu-base ships no generated locales at all" 이라는 주석과 함께 `LANG=C` 가 박혀 있었다. **주석이 틀렸다.** rootfs 에는 `/usr/lib/locale/C.utf8` 이 있다:

```
$ ls $R/usr/lib/locale/
C.utf8
$ ls -d /usr/lib/locale        # 호스트
ls: cannot access '/usr/lib/locale': No such file or directory
```

glibc 의 `_nl_find_locale` 이 리터럴 `/usr/lib/locale` 을 내부 호출로 여는데 — 또 §6.17 계열이다 — 호스트에는 그 디렉토리가 **아예 없다.** 그래서 게스트는 `C` 와 `POSIX` 밖에 못 봤다.

**수정**: glibc 자신의 탈출구인 `LOCPATH` 를 rootfs 쪽으로 지정하고 기본 로케일을 `C.UTF-8` 로 올린다.

```
$ alr run /usr/bin/tmux -V
tmux 3.4
$ alr run /usr/bin/python3 -c 'import sys;print(sys.getdefaultencoding(), sys.stdout.encoding)'
utf-8 utf-8
```

**한계 (문서화)**: `LOCPATH` 가 설정되면 glibc 는 `locale-archive` 를 건너뛴다. 이후 추가 로케일은 디렉토리로 생성해야 한다 — `locale-gen --no-archive`.

## 5. `php-cli` — 우리 탓이 아님을 증명한 방법

유일하게 남은 실행 실패:

```
$ php --version
*** buffer overflow detected ***: terminated      (rc=134)
```

`python3`, `ruby`, `perl`, `node`, `git` 은 전부 정상이다. preload 초기화 직후, 우리가 로그를 남기는 어떤 래퍼보다도 먼저 죽는다.

추측하지 않고 **대조 실험 두 번**을 했다.

**대조 1 — NSS 백엔드 제거.** `ALR_NO_NSS` 컴파일 가드로 §M10 의 NSS 구현을 통째로 뺀 빌드를 배포:

```
배포본 NSS 심볼: 0
getent group root  →  (빈 출력)        ← 대조군이 실제로 작동함을 확인
php --version      →  *** buffer overflow detected ***
```

> 첫 시도에서 이 대조는 **무효였다.** `dev-push.sh preload` 가 내부에서 재빌드하면서 `ALR_CFLAGS_EXTRA` 를 전달받지 않아 NSS 포함 빌드가 배포되었다. 배포본 심볼을 세어 보고서야 알았다. 대조군이 실제로 대조가 되는지부터 확인해야 한다.

**대조 2 — 인터포지션 전체 제거.** 아무 심볼도 정의하지 않는 빈 `.so` 를 preload 자리에 놓고:

```
alr run /bin/echo ok      →  ok                                  ← 실행 경로는 살아 있음
alr run /usr/bin/php ...  →  *** buffer overflow detected ***
```

**결론: `php-cli` 의 abort 는 우리 래퍼가 원인이 아니다.** 로더를 명시적으로 호출하는 실행 방식(ADR 0002) 자체 또는 php 쪽 문제다. 근본 원인은 **아직 미확인** 이며, `KNOWN_FAIL:php-abort-unattributed` 로 남긴다.

## 6. 최종 상태

| 지표 | 값 |
|---|---|
| 호환성 폭 — 설치 | **96 / 96** |
| 호환성 폭 — 실행 | **95 / 96** (php-cli 만 실패, 귀속 완료) |
| 수용 테스트 | **PASS=60 FAIL=0 KNOWN_FAIL=1** |
| 남은 KNOWN_FAIL | `/dev/full` 미에뮬레이션 |

> ⚠️ **2026-08-03 정정 — 이 표는 제품이 아니라 "그때 존재하던 테스트"에 대한 진술이었다.**
> `KNOWN_FAIL=1` 과 `96/96` 은 당시 수용 테스트가 검사하던 범위에서만 참이다. 그 시점에 **두 개의 갭이 코드에 살아 있었고 어느 카운트에도 나타날 수 없었다** — 검사하는 테스트가 없었기 때문이다:
>
> - `posix_spawn`/`posix_spawnp`/`system`/`popen` 미구현 → **`make` 가 `Error 127` 로 깨져 있었다.** breadth 의 `build-essential` 검사가 `gcc` 를 셸로 직접 불러 통과했기에 가려졌다.
> - `gethostby*` 계열 미구현, 게스트 `/etc/hosts` 소비자 없음.
>
> 둘 다 [M12](2026-08-03-m12-spawn-resolver.md) 에서 수정했고 회귀 테스트를 붙였다. 교훈은 수치 자체가 아니라 **커버리지의 한계를 같이 적어야 한다**는 것이다 — 테스트가 없는 영역은 PASS 로도 FAIL 로도 세어지지 않고 그냥 보이지 않는다.

이 라운드에서 함께 닫힌 이전 KNOWN_FAIL:

- `/proc/mounts` 호스트 마운트 테이블 노출 → 합성 테이블. `df` 가 쓰는 `setmntent` 경로 포함. 누출 검사 0건
- `/proc/self/status` 로더 이름 노출 → `prctl(PR_SET_NAME)`. `status`·`comm`·`ps` 세 뷰가 한 번에 정정됨

## 7. 덤으로 드러난 결함 — exec 경유 신원

수용 테스트를 고치다가 잡혔다. `PR_SET_NAME` 을 넣고 나니 `bash -c '...'` 로 띄운 자식의 이름이 `bash` 로 남았고, 확인해 보니 이름만의 문제가 아니었다:

```
$ alr run /bin/bash -c 'readlink /proc/self/exe'
/bin/bash                      ← 자기 자신이 아니라 부모
```

exec 재디스패치가 부모의 `ALR_GUEST_EXE` 를 그대로 물려주고 있었다. [04-preload-spec.md §7](../04-preload-spec.md) 이 **하드 요구사항** 으로 못박은 바로 그 항목이 셸을 한 단계만 거치면 깨져 있었다 — Node 의 `process.execPath` 가 이 readlink 이고, npm 은 셸 래퍼를 통해 거기서 node 를 재spawn 한다.

수정 후:

```
$ alr run /bin/bash -c 'readlink /proc/self/exe'      →  /usr/bin/readlink
$ alr run /bin/bash -c 'node -p process.execPath'     →  /usr/local/bin/node
$ alr run /bin/bash -c 'bash -c "cat /proc/self/comm"' →  cat
```

`ALR_NODE_EXECPATH` 테스트가 통과하고 있었는데도 깨져 있었던 이유는, 그 테스트가 node 를 **직접** 실행했기 때문이다. 이 세션에서 반복된 패턴이다: **실제 소비자가 쓰는 경로로 검증해야 한다.**

## 8. 절차 교훈

이 라운드에서 세 번, 실패의 원인이 제품이 아니라 **내 검증 장치** 였다.

1. `/tmp` 리다이렉트 실패 → 96개 전부 "설치 불가"
2. `dev-push.sh accept` 가 `ALR_DISTROS_DIR` 을 무시 → 통과하는 테스트 9개가 FAIL
3. `dev-push.sh preload` 가 `ALR_CFLAGS_EXTRA` 를 무시 → 대조 실험이 무효

세 번 모두 **배포본을 직접 확인**해서 잡았다(`strings`, `llvm-readelf`, 대조군의 기대 실패). 실패를 코드 탓으로 돌리기 전에 어느 바이너리가 실제로 실행되는지부터 확인한다 — [M9 최종 정정](2026-08-02-m9-reproducibility.md) 과 같은 규칙이다.
