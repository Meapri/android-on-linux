# M19 — 참조 기기 #2 (Snapdragon): 차단 집합은 SoC·커널과 무관하다

- **날짜**: 2026-08-03
- **기기**: Samsung SM-S937N (Galaxy S25 Edge), Snapdragon 8 Elite SM8750 (`ro.board.platform=sun`)
- **OS**: Android 16, SELinux Enforcing, 커널 `6.6.98-android15-8-pd6ff1cd-abogkiS937NKSS9CZG3-4k`
- **컨텍스트**: `uid=10447  u:r:untrusted_app_27:s0  Seccomp=2`
- **목적**: 이 저장소가 가장 오래 달고 있던 `PENDING_DEVICE` — [§A6](../01-platform-facts.md)의 "차단 239개는 이 기기의 집합인가, Android의 집합인가"

참조 #1은 SM-X236N / MediaTek MT8775 / 커널 6.1.145-android14 다. 두 기기는 **SoC 벤더와 커널 major.minor가 모두 다르고**, Android 릴리스만 같다.

## 0. 측정 자격부터

```
uid       : 10447
seccomp   : 2
selinux   : u:r:untrusted_app_27:s0:c191,c257,c512,c768
```

`uid>=10000 ∧ Seccomp=2` 가 아니면 이 문서의 모든 숫자가 허구다. Android 앱 seccomp 필터는 zygote가 uid≥10000으로 띄운 프로세스에만 설치되고, `adb shell`은 `Seccomp: 0`으로 나온다. 하네스가 게이트를 들고 있으며([`scripts/dev-push.sh`](../../scripts/dev-push.sh) `assert_context`), 통과 후에만 진행했다.

## 1. §A6 — 차단 집합 239개가 완전히 동일하다

| | 참조 #1 | 참조 #2 |
|---|---|---|
| SoC | MediaTek MT8775 | **Qualcomm** SM8750 |
| 커널 | 6.1.145-**android14** | **6.6.98-android15** |
| 차단 | 468개 중 **239** | 468개 중 **239** |

개수만이 아니라 **집합이 같다**:

```
$ scripts/diff-sweep.sh docs/evidence/sweeps/mediatek-mt8775-android16-k6.1.txt \
                        docs/evidence/sweeps/snapdragon-8elite-android16-k6.6.txt
  shared: 239
ALR SWEEP DIFF: IDENTICAL (239 syscalls, both devices)
```

### 1.1 결정적인 부분은 개수가 아니라 음성 주장이다

`alr_sigsys_table.h`는 참조 #1에서 **차단되지 않는다**고 명시적으로 단언한 세 개를 갖고 있다 — `setresuid`(147), `getresuid`(148), `getresgid`(150). 참조 #2에서도 셋 다 차단되지 않는다.

이게 왜 중요한가: 차단되는 자격증명 계열은 143·144·145·146·149·151·152다. 147/148/150은 **그 사이에 끼어 있다.** 만약 두 기기가 "대충 비슷한 범위를 막는" 서로 다른 필터를 갖고 있었다면 이 셋 중 하나는 갈렸을 것이다. 갈리지 않았다는 것은 두 필터가 같은 목록에서 생성됐다는 뜻이다 — 개수 일치의 우연이 아니라 **지문 일치**다.

### 1.2 그래서 무엇이 확정되고 무엇이 남았나

**확정**: `alr_sigsys_table.h`를 릴리스에 동봉하는 현재 방식이 옳다. 표는 기기별 생성물이 아니라 **기본값**이다. OEM·SoC·커널 버전은 무관하다.

**남음**: 두 기기 모두 **Android 16**이다. 갈린 축(SoC 벤더, 6.1→6.6, android14→android15)은 전부 무관했는데, **정작 allowlist가 실제로 따라가는 축은 갈리지 않았다** — bionic의 allowlist는 릴리스마다 커졌다(android12 365줄 → android16 392줄). 즉 이 결과는 "OEM은 상관없다"의 강한 증거이지 "Android 버전도 상관없다"의 증거가 아니다. Android 12~15 한 대가 남은 전부다.

### 1.3 하마터면 "비교 불가"로 끝날 뻔했다

diff를 시작할 때 `alr_sigsys_table.h`에서 `{ N, ... }` 표 행을 grep해 **30개**를 얻었다. 참조 #2는 239개다. 여기서 *"큐레이션된 예외만 남기고 원본 스윕은 폐기됐다 — 전체 diff는 참조 #1을 다시 손에 넣어야 가능하다"* 로 결론 내리고, 그 문장을 헤더에 커밋까지 했다.

틀렸다. 전체 239개는 **같은 파일 끝의 `#if 0` 블록**에 처음부터 있었고, [§A6](../01-platform-facts.md)이 그렇게 적어 두기까지 했다("그 헤더 끝의 `#if 0` 블록이 기기 ground truth이며, 회귀 diff의 기준선이다"). 내 grep이 표 행 문법만 찾았을 뿐이다.

**이 세션 다섯 번째 "부재 오독"이고, 앞선 넷과는 결이 다르다.** [M18 §5](2026-08-03-m18-codex-config.md)의 넷은 전부 *출력을 자르는 명령*(`head`·`grep -c`·`wc -l`)이 원인이었다. 이번엔 자르지 않았다 — **한 가지 문법으로만 찾고 못 찾자 없다고 했다.** 처방도 다르다: 부재를 주장하기 전에 **그 사실이 있다면 어디에 적혀 있을 문서를 먼저 읽는다.** §A6에 답이 있었고 나는 그것을 읽지 않은 채로 파일을 grep했다.

원본 스윕은 이제 [`docs/evidence/sweeps/`](sweeps/)에 한 줄에 하나씩 들어간다. 다음 비교는 `scripts/diff-sweep.sh` 한 줄이다.

**그리고 복원본이 옳았는지 확인했다** — `MEASURED` 2026-08-03 (같은 날 늦게). 참조 #1 을 다시 연결해 `alr doctor` 로 **처음부터 다시 스윕**하고 복원 파일과 diff 했다:

```
  A  mediatek-mt8775-android16-k6.1.txt   239 blocked   ← #if 0 에서 복원한 것
  B  (live re-sweep)                      239 blocked
ALR SWEEP DIFF: IDENTICAL (239 syscalls, both devices)
```

즉 (1) 복원이 충실했고, (2) 위 §1 의 기기 간 비교가 **훼손된 재구성이 아니라 진짜 ground truth** 를 상대로 한 것이며, (3) 차단 집합이 세션을 넘어 안정적이다(최초 스윕 2026-08-02). 복원본을 근거로 결론을 낸 뒤 원본으로 검산한 셈이다.

## 2. ADR 0006 — SUD는 커널 6.6에서도 없다

[ADR 0006](../adr/0006-raw-syscall-binaries.md)은 raw `svc` 바이너리를 네이티브 속도로 가로챌 방법이 없다고 결론지었고, 근거 중 하나가 커널 6.1에서 `PR_SET_SYSCALL_USER_DISPATCH`가 arm64에 없다는 것이었다. 커널이 올라간 기기에서 다시 쟀다:

```
SUD      : UNAVAILABLE (range=Invalid argument empty=Invalid argument)
NOTIF    : LISTENER fd=3
FILTER   : INSTALLED
```

인자 두 형태 모두 `EINVAL`. **커널 6.6.98에서도 arm64 SUD는 없다.** seccomp user notification은 여기서도 붙지만, 그 비용은 이미 재 놓았다 — 154 µs/syscall([M-노티프 측정](../adr/0006-raw-syscall-binaries.md)). ADR 0006은 두 기기에서 유효하다.

## 3. ADR 0005 — Play 스토어 빌드를 처음으로 실측했다

[ADR 0005](../adr/0005-play-store-unsupported.md)는 GitHub 빌드(`targetSdk=28`)를 요구한다. Play 빌드가 왜 안 되는지는 **추론**이었고 실물을 잰 적이 없었다. 이 기기는 Play 빌드가 깔린 채로 왔다:

| | Play 빌드 | GitHub 빌드 |
|---|---|---|
| `versionName` | `googleplay.2026.06.21` | `0.118.3` |
| `targetSdk` | **37** | **28** |
| `minSdk` | 32 | 24 |
| `installerPackageName` | `com.android.vending` | `null` |

**ADR 0005의 전제가 `MEASURED`가 됐다** — Play 빌드는 실제로 `targetSdk=37`을 싣는다.

**결론은 여전히 추론이다.** Play 빌드에서 `alr`이 못 도는 것까지 잰 것은 아니다 — GitHub 빌드를 설치하려면 서명이 달라 Play 빌드를 **먼저 지워야** 했고(`INSTALL_FAILED_UPDATE_INCOMPATIBLE ... signatures do not match`), 지운 뒤에는 잴 대상이 없다. `targetSdk>=29`의 W^X 규칙에서 앱 데이터 디렉토리 실행이 막힌다는 플랫폼 사실로부터의 연역이 근거의 전부다.

교체 자체도 기록해 둔다: GitHub 빌드는 디버그 서명이라 `run-as com.termux`가 통하고, 그 덕에 UI를 거의 건드리지 않고 `authorized_keys`·`openssh`·`clang`을 넣을 수 있었다. Play 빌드에서는 이 경로가 없다.

### 4.1 ldconfig 다이버전이 진짜 업그레이드를 견뎠다

게스트에 `libc6-dev make python3 gcc`를 넣는 과정에서 `libc-bin`이 **2.39-0ubuntu8.7 → 8.8**로 올라갔다. 다이버전은 살아 있다:

```
local diversion of /usr/sbin/ldconfig to /usr/sbin/ldconfig.distrib
```

참조 #1에서는 이 경로를 억지로(강제 unpack) 밟게 해서 확인했다. 여기서는 **평범한 apt 업그레이드가 자연히 밟았고** 결과가 같았다.

## 5. 87/96은 기기 차이가 아니라 내 하네스 충돌이었다

첫 breadth 실행은 `install=87/96 run=87/96`으로 나왔다. 9개 실패의 dpkg 상태가 `triggers-pending`·`unpacked`·`absent`로 제각각이라 기기 차이를 의심할 만했다. apt 로그를 열자 원인이 하나였다:

```
108 E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 15272 (apt-get)
```

**앞서 10분 타임아웃으로 끊은 breadth 실행이 기기에서는 계속 돌고 있었다.** 타임아웃은 SSH 클라이언트를 죽였을 뿐 원격 프로세스를 죽이지 않는다. 그 상태에서 두 번째 실행을 띄웠고, 배치 12개가 전부 락에 막힌 뒤 개별 재시도로 87개만 겨우 붙은 것이다.

정리 후(고아 없음 확인 → `dpkg --configure -a` → 파손 0건) 단독으로 재실행하니 **96/96, 락 에러 0건**이었다.

교훈 두 개:

- **오래 도는 기기 작업은 분리해서 띄우고 폴링한다.** 클라이언트 타임아웃은 취소가 아니다.
- 이 저장소가 반복해 온 규칙이 또 맞았다 — **이상한 수치를 만나면 대상이 아니라 계측기를 먼저 본다.** 여기서는 apt 로그가 한 줄로 답했다.

## 6. 성능 — A/B

### 6.1 히어로 벤치 — `git status` 10k, **양쪽 git 2.53.0**

M8 의 `git status` 비교에는 약점이 있었고 문서가 그렇게 적어 두었다: 세 실행의 git 빌드가 달랐다(2.55/2.43/2.53). 여기서는 그것을 없앴다. proot-distro 가 제공하는 ubuntu 는 **26.04**(git 2.53.0)뿐이므로, alr 쪽도 26.04 게스트를 깔아 **같은 배포판·같은 git 버전**으로 맞췄다.

| | git | `git status --porcelain` (10,000 파일, 워밍업 1회 버리고 7회 중앙값 `[min-max]`) |
|---|---|---|
| native (Termux) | 2.55.0 | **33 ms** `[28-40]` |
| **alr** | 2.53.0 | **36 ms** `[34-44]` |
| proot-distro | 2.53.0 | **930 ms** `[873-971]` |

**alr 은 네이티브와 3 ms 차이이고, proot 대비 25.8배다.**

**이 워크로드는 §6.2 의 exec 처리량과 달리 안정적이다.** 워밍업 없이 잰 첫 측정이 37 / 39 / 947 ms 였고, 워밍업을 넣은 뒤 33 / 36 / 930 이다 — 세 다리 모두 스프레드 안이다. exec 처리량이 330↔707 로 두 배 갈렸던 것과 대조된다. 워밍업 여부가 워크로드마다 다르게 작용하므로, **어느 쪽인지 모르면 둘 다 재 보는 것 말고 방법이 없다.**

native 다리만 여전히 다른 빌드다(Termux 의 git 2.55.0). alr/proot 쌍은 동일 버전이므로 **25.8배 쪽이 엄밀한 수치**이고, native 대비 1.09배는 근사치로 읽어야 한다.

양성 대조를 먼저 돌렸다. 첫 시도에서 alr 16 ms / proot 239 ms 라는 좋아 보이는 숫자가 나왔는데, **저장소가 아예 만들어지지 않은 상태였다** — 26.04 의 `mkdir` 은 uutils 라 동작하지 않았고, 나는 없는 디렉토리에 대해 git 이 에러 내는 시간을 재고 있었다. 파일 수를 찍어 둔 덕에 걸렸다. 최종 측정 전에 확인한 것:

```
tracked 파일 : alr 10000 / proot 10000
파일 하나 수정 후: alr " M f4242" / proot " M f4242"     <- 실제로 10k 를 훑는다
```

파일 트리는 **Termux 호스트가** 만들었고 git 만 게스트에서 돌렸다. 26.04 게스트에서 git 은 정상 동작한다([ADR 0006 추가 실측](../adr/0006-raw-syscall-binaries.md)).

### 6.2 하네스 A/B (24.04 게스트) — 그리고 첫 수치를 버린 이유

```
ALR BENCH NODE COLD vs PROOT:  5.49x  alr 53 [50-57] / proot 291 [285-299] ms  (identical node binary)
ALR BENCH EXEC THROUGHPUT:     707 exec/s  alr 707 / proot 224 exec/s  (alr 283 ms [252-298] over 200 execs)
ALR MEDIATION INVARIANT:       PASS  path_traps=0 syscall_stops=0
```

node 는 게스트의 `/opt/node` 를 proot rootfs 로 통째로 복사해 **바이트 단위로 동일한 바이너리**임을 `cmp` 로 확인한 뒤 쟀다.

**처음 이 문서에 적었던 수치는 `330 exec/s` / `61 ms` 였고, 2배 틀렸다.** 그 실행은 breadth 스위트가 96개 패키지를 설치한 **직후**였다 — 발열 제한이 걸리고 페이지 캐시가 밀린 기기를 잰 것이다. 같은 폰, 같은 바이너리로 잠시 뒤 세 번 더 돌린 결과:

| 회차 | exec/s | node 콜드 |
|---|---|---|
| **breadth 직후** | **330** | **61 ms** |
| 이후 1 | 687 | 52 ms |
| 이후 2 | 692 | 51 ms |
| 이후 3 | 683 | 55 ms |

안정 상태는 ±1% 로 촘촘하고, **이상치는 첫 번째 하나뿐이다.** 5회 중앙값을 쓰는 것으로는 이걸 못 막는다 — **다섯 번 다 발열 상태였기** 때문이다.

그래서 하네스를 고쳤다:

- **버리는 워밍업 1회**를 모든 측정 앞에 넣는다.
- 중앙값만이 아니라 **스프레드 `[min-max]`** 를 함께 출력한다. 기기가 안정되지 않았으면 숫자가 스스로 드러낸다.

`median_ms` 가 스프레드를 전역 변수로 넘기려던 첫 시도는 **명령 치환이 서브셸이라** 조용히 빈 값이 됐다. 자리표시자 `[]` 를 출력하고 있었던 덕에 눈에 띄었다 — 값을 생략했다면 못 봤을 것이다.

> **참조 #1 의 351 exec/s 도 같은 의심을 받았고, 해소됐다.** 같은 날 늦게 그 기기를 다시 연결해 **워밍업 규율을 적용한 하네스로** 재측정했다: **342 exec/s** (proot 131), node 콜드 **51 ms** `[44-60]` (proot 338 `[330-341]`). 워밍업 없던 원래 값 351 / 55 ms 와 사실상 같다. **즉 발열 이상치는 Snapdragon 의 breadth 직후 실행에만 해당했고, MediaTek 원래 수치는 유효했다.** 아래 표는 이제 **양쪽 다 워밍업 후** 값이다.

### 6.3 배수는 기기마다 다르다 — 인용할 때 기기를 붙인다

| | 참조 #1 (MediaTek) | 참조 #2 (Snapdragon) |
|---|---|---|
| `node -e 0` 콜드 | **6.63×** (alr 51 `[44-60]` / proot 338 `[330-341]` ms) | **5.49×** (alr 53 `[50-57]` / proot 291 `[285-299]` ms) |
| exec 처리량 | **342 exec/s** (proot 131) | **707 exec/s** (proot 224) |
| 재작성 총비용 | **38.2 µs** | **73.6 µs** |
| `git status` 10k | 34.8× (git 빌드 3종 상이 — 인용 안 함) | **25.8×** (git 동일 버전) |

**이제 두 열은 같은 조건이다** — 양쪽 다 워밍업 1회 폐기 후 측정했다. 그러므로 나란히 읽어도 된다.

읽는 법: **exec 는 Snapdragon 이 2배 빠르고**(342 → 707, proot 쪽도 131 → 224 로 함께 오르므로 기기 성능 차이다), **재작성 per-op 은 MediaTek 이 빠르다**(abs 58.9 ns vs 93–129 ns). 배수가 MediaTek 쪽에서 더 큰 것(6.63× vs 5.49×)은 alr 이 거기서 더 빨라서가 아니라 **proot 가 더 느려서**다 — [M17 §3](2026-08-03-m17-bench-ab.md) 이 콜드 스타트에 대해 한 말 그대로다.

배수 자체([M17 §3](2026-08-03-m17-bench-ab.md) 이 콜드 스타트에 대해 한 말)는 여전히 유효하다 — 큰 배수는 "alr 이 빠르다"가 아니라 "proot 가 느리다"는 진술이다.

`git status` 의 34.8× → 25.8× 하락은 기기 차이와 **git 버전 통일**이 섞여 있어 분리되지 않는다. 더 엄밀한 쪽이 25.8× 이므로 앞으로는 이쪽을 인용한다.

### 6.4 회귀 기준선이 기기를 섞고 있었다

`bench/baseline.json` 은 평평했다 — 기기 구분 없이 `node_cold_ms: 57.0` 하나. Snapdragon 의 첫 결과가 그것과 비교되어 **`ok`** 를 받았는데, 그건 회귀 판정이 아니라 서로 다른 폰 두 대의 차이였다. 이제 `tests/device/bench.sh` 가 `ALR BENCH DEVICE:` 줄을 내고 기준선을 **기기별로** 건다. 기기 정보가 없으면 게이트는 비교를 건너뛴다(다른 기기 값과 재느니).

그리고 그 과정에서 게이트 스크레이퍼가 **다른 줄의 숫자로 답할 수 있다**는 것이 드러났다. `node_cold_ms` 패턴이 `re.S` 아래 `.*?` 였던 탓에, 출력 형식이 바뀌자 자기 줄에서 매칭에 실패하고 **다음 줄의 exec 처리량 683 을 집어 `683 ms` 로 기록**했다 — `--update` 가 그걸 기준선에 사실로 써 넣었다. 잘못 매칭하는 정규식은 잘 동작하는 정규식과 겉모습이 같다. 그래서 정답이 알려진 고정 트랜스크립트에 대한 `--self-test` 를 넣고 CI 에 걸었다. 옛 정규식을 되돌려 넣으면 실제로 `FAIL` 한다는 것까지 확인했다.

`tests/device/bench.sh` 말미의 안내가 "MediaTek MT8775" 를 하드코딩하고 있던 것도 함께 고쳤다.

## 7. 하드 게이트 하나가 이 기기에서 깨진다 — `PRELOAD RW ABS COST`

`docs/04-preload-spec.md §13` 은 `rw()` 절대경로 히트에 **≤ 100 ns/op** 예산을 걸어 두었고, 회귀 게이트가 그것을 하드 불변식으로 들고 있다. **참조 기기 #2 에서 이 게이트는 통과하지 않는다.**

| 시점 | `RW ABS COST` | `getppid` 교정 |
|---|---|---|
| 세션 초반 1회 | **79.2 ns** PASS | 288 ns |
| 이후 연속 7회 | **106 – 115 ns** FAIL | 320 – 356 ns |

2분 냉각 후에도 106–113 이다. **79.2 쪽이 이상치**로 보인다 — 세션 시작 시점의 차갑고 부스트된 기기에서 한 번 난 값이고, 그 뒤 어떤 조건에서도 재현되지 않았다.

측정 잡음부터 걷어냈다. `bench_one()` 은 이제 **7회 중 최솟값**을 쓴다 — 잡음(느린 코어, 낮은 클럭, 선점)은 전부 시간을 **더하기만** 하므로, 순수 CPU 바운드 문자열 연산에서는 최솟값이 코드 자체의 비용에 가장 가깝다. 그래도 106–115 다. 즉 게이트 실패는 계측 잡음이 아니다.

비율도 안정적이지 않다 — `RW/getppid` 가 0.275 → 0.33–0.35 로 움직인다. 절대값도 비율도 기기·상태를 넘어 이식되지 않는다.

### 7.1 그런데 이 게이트가 지키려는 것은 통과한다

같은 §13 이 **총비용 예산**도 함께 걸어 두었다: `git status` 10k 의 재작성 총비용 **≤ 1.5 ms**. 그쪽을 이 기기의 실측값으로 계산하면:

```
경로 호출 9,912회 중 실제 재작성 26회 (M8)
  상대경로 미스  9,886 × 6.0 ns  =  59 µs
  절대경로 히트     26 × 111 ns  =   3 µs
  합계                            ≈  62 µs      예산 1,500 µs 의 1/24
```

**per-op 100 ns 는 프록시이고, 그 프록시가 지키려던 총비용은 24배 여유로 통과한다.** `git status` 실측(36 ms, 네이티브 33 ms)이 같은 이야기를 다른 방향에서 한다 — 경로 계층이 3 ms 를 먹었다면 그 수치가 나올 수 없다.

### 7.2 임계값을 올리지 않고, 게이트를 옮겼다

올리면 초록이 되지만 그건 측정이 아니라 목표를 옮기는 것이다. 대신 §13이 이미 적어 둔 **총비용 예산**을 하드 게이트로 만들었다. 그 전에 계측기부터 고쳐야 했고, 세 군데가 망가져 있었다.

**(1) 프로세스를 통째로 흘리고 있었다.** `ALR_COUNT=1 alr run /bin/echo hi` 가 카운터 줄을 **10회 중 0회** 냈고 `/bin/true` 는 10회 중 10회 냈다 — 경합이 아니라 결정적이다. GNU coreutils 는 gnulib `close_stdout` 을 atexit 로 등록하고 그것이 **stderr 까지 닫는다.** glibc 는 atexit 핸들러를 `.fini_array` 소멸자보다 **먼저** 돌리므로, 총계를 찍을 때 fd 2 는 이미 없다. `alr` 은 `ALR_LOG_FD=2` 를 넘기고 있었다. 합산 게이트를 그 위에 세웠다면 파이프라인의 coreutils 프로세스가 전부 빠진 채 **낙관적으로 통과**했을 것이다.

**(2) 분류가 전사가 아니었다.** 재작성도 sysdir 도 아닌 절대경로가 `else` 없는 if/else-if 를 빠져나가 `total` 에만 잡혔다 — `10067` 대 `28+10008+1=10037`. 카운터 없는 버킷은 비용 모델이 **0원으로 매기는** 버킷이다.

**(3) 카운터가 경합했다.** git 인덱스 갱신이 멀티스레드라 평범한 `++` 가 10006 중 119(1.2%)를 잃었다. 단일 스레드인 `id`·`cat` 은 정확했다. 이제 `__atomic_fetch_add` 이고, 버킷 합이 total 과 정확히 일치하며 5회 연속 동일하다.

고친 뒤의 실측 총비용은 **73.6 µs** 다(예산 1,500 µs). 이전 `rw_cost.c` 의 MODELED 값은 절대경로 단가를 13,500회 **전부**에 곱해 약 24배 과대였고, 그 오차 덕에 1.5 ms 예산과 얼추 맞아 보였다.

### 7.3 per-op 는 폰에서 2배보다 잘 재현되지 않는다

per-op 를 안정화하려고 세 가지를 순서대로 넣었고, 결과는 정직하게 말해 **약 2배**다:

| 조치 | abs 스프레드(6회) |
|---|---|
| best-of-7 라운드 | 76.0 – 102.7 ns |
| + 300 ms 시간 기반 워밍업 | 57.8 – 129.3 ns (**이봉분포**) |
| + 앱이 쓸 수 있는 가장 빠른 코어에 고정 | 66.6 – 128.9 ns (rel 은 7.4 로 수렴) |

이봉분포는 big.LITTLE 배치다. Android 가 앱을 cpuset 에 가두어 **8코어 중 4개만** `sched_setaffinity` 를 받으므로, 기기를 조용한 곳으로 데려갈 수가 없다. 그래서 기기별 허용치는 **2.5×** 이고, 이건 게을러서가 아니라 **실측 잡음 바닥**이다.

### 7.4 대심문이 내가 방금 커밋한 게이트에서 false-green 셋을 찾았다

여기가 이 절에서 제일 중요하다. 위 설계를 커밋한 뒤 적대적 검토를 돌렸고, **셋 다 재현됐다**:

| | 증상 |
|---|---|
| 고정 실패한 실행 | per-op 4개가 전부 `SKIP` 되고 **abs 46배 회귀가 `GATE: PASS`** |
| 실패한 실행에 `--update` | 4334.7 ns 가 **기준선에 기록**되어 다음 실행이 초록 |
| 0 믹스 | `have_mix` 가 위치 인자 판정뿐이라 `0.0 us <= 1500 PASS` |

두 번째가 가장 나쁘다 — **goalpost 이동 장치가 게이트 안에 들어 있었다.**

그리고 총비용 게이트 혼자로는 대신할 수 없다는 계산이 나왔다. 이 기기 기준선으로 절대경로는 총비용의 3.4% 라, **548배** 회귀해야 1,500 µs 가 빨개진다. §5.1 이 적으로 지목한 4,334.7 ns/op 변환기는 총 195 µs 로 **7.7배 여유로 통과**한다. 즉 `rw_total_us` 는 워크로드 형태 감지기이지 per-op 성능 게이트가 아니다.

**해법은 건너뛸 수 없는 절대 천장이다.** 두 참조 기기에서 기록된 최악값의 약 4배(abs 500 / rel 40 / sysdir 150 / under 500 ns)로 두어, 기기 차이·발열·고정 실패 어느 것도 닿지 못하되 40배급 회귀는 어떤 상태에서든 걸린다. `--update` 는 실패한 실행에서 기록을 **거부**하고, 기준선 없는 기기는 `--allow-new-device` 없이는 조용히 통과하지 못한다.

**구조적 교훈**: 내 자기시험은 **스크레이퍼만** 검사하고 있었다. 세 구멍은 전부 스크레이핑 버그가 아니라 **판정 버그**였고 그래서 통과했다. 이제 시나리오 표가 판정(종료 코드)을 검사하고, 각 수정을 되돌리면 실제로 FAIL 하는 것까지 확인했다.
