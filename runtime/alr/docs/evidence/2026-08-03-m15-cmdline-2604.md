# M15 — `/proc/self/cmdline` 합성, 그리고 26.04 가 지원 불가인 이유

- **날짜**: 2026-08-03
- **기기**: MediaTek arm64, `uid=10297 Seccomp=2 u:r:untrusted_app_27:s0`
- **수용 테스트**: **PASS=78 FAIL=0 KNOWN_FAIL=2** (이전 76/0/1 + `ALR CODEX LINKAGE` 재계상)
- **호환성 폭 (24.04)**: 96/96 설치, 96/96 실행 — 회귀 없음

## 1. `/proc/self/cmdline` — 스펙 §7이 요구했고 구현되지 않았던 것

로더를 명시적으로 부르는 설계(ADR 0002) 때문에 게스트의 `cmdline` 은 이렇게 보였다:

```
/data/.../lib/ld-linux-aarch64.so.1 --library-path /data/data/com.termux/... \
  --inhibit-cache --argv0 /bin/cat --preload /data/.../libalr_preload.so \
  /data/.../bin/cat /proc/self/cmdline
```

**호출 전체와 모든 호스트 경로가 노출된다.** `docs/04-preload-spec.md` §7 은 이것을 합성하라고 명시했지만 구현된 적이 없었다.

**수정**: 진짜 `cmdline` 을 읽어 우리가 emit 하는 로더 옵션(`--library-path`/`--preload`/`--argv0`/`--inhibit-cache`)을 걸어 넘긴 뒤, `--argv0` 값을 argv[0] 으로 삼고 프로그램 경로 **뒤**의 인자들을 이어 붙인다. 새 환경변수가 필요 없다 — 필요한 정보가 이미 명령줄에 있다. 로더를 거치지 않은 프로세스(정적 바이너리, CLI 자신)는 첫 항목이 `ld-linux*` 가 아니므로 그대로 통과시킨다.

`cmdline` 은 NUL 구분이라 `strlen()` 이 거짓말을 한다 — 길이를 따로 들고 다닌다.

```
$ alr run /bin/cat /proc/self/cmdline | tr '\0' ' '
/bin/cat /proc/self/cmdline
```

회귀 테스트 `PRELOAD PROC CMDLINE`, `PRELOAD CMDLINE NO HOST PATH` 추가.

> 두 테스트를 처음 쓸 때 둘 다 자기 발에 걸렸다. 하나는 게스트 셸을 경유해 **셸의 argv** 를 읽었고(합성은 정상인데 기대값이 틀렸다), 다른 하나는 `grep -q /data/data` 를 게스트 명령줄에 넣는 바람에 **패턴이 자기 자신을 매치**했다. 지금은 `cat` 으로 직접 읽고 호스트 쪽에서 변환한다.

## 2. Ubuntu 26.04 — 정확히 무엇이 되고 무엇이 안 되는가

먼저 다운로더를 일반화했다. 24.04 는 포인트 릴리스가 붙고(`ubuntu-base-24.04.4-base-arm64.tar.gz`) 26.04 는 붙지 않는다(`ubuntu-base-26.04-base-arm64.tar.gz`). 양쪽 이름을 모두 매치하고, 여러 개면 가장 높은 포인트 릴리스를 고른다.

```
$ ALR_DISTRO=ubuntu-26.04 alr install
alr: resolving the current ubuntu-base image for 26.04
alr: .../ubuntu-base-26.04-base-arm64.tar.gz
alr: sha256 ok
alr: absolute symlinks: 20 relativized, 0 failed
alr: installed .../ubuntu-26.04
```

설치·검증·추출·심링크 상대화·ldconfig diversion 전부 정상이다. 부팅도 한다.

| 동작 | 실패 |
|---|---|
| `bash` `dpkg` `apt-get` `find` `grep` `sed` `awk` `tar` `getent` | **uutils coreutils 계열 전부** (`ls` `cat` `echo` `head` …) |

즉 "26.04 는 부팅하지 않는다" 는 [M14 §3](2026-08-03-m14-ioctl-php.md) 의 기록은 **부정확했다.** 26.04 는 부팅하고 apt 도 돈다. 깨지는 것은 coreutils 하나다.

Ubuntu 26.04 는 coreutils 를 **uutils(Rust) 멀티콜 바이너리**로 교체했다. `/bin/echo -> ../lib/cargo/bin/coreutils/echo` 이고 모든 도구가 같은 10.5 MB 바이너리를 가리킨다. 이것이 자기 이름을 해석하지 못한다:

```
coreutils: unknown program 'ld-linux-aarch64.so'
```

`.1` 이 떨어진 것은 Rust `Path::file_stem()` 의 흔적이다.

## 3. 규명 — 배제 끝에 찾은 것

**측정으로 배제한 것.** 계측기가 실제로 작동하는지 먼저 확인한 뒤(C 프로브의 `readlink(/proc/self/exe)` 가 트레이스에 잡히는 것으로) 실패하는 프로세스를 관측했다:

| 가설 | 측정 결과 |
|---|---|
| `argv[0]` 이 로더다 | **아니다.** preload 생성자가 찍은 값: `argc=2 argv[0]=/bin/echo argv[1]=x` |
| `/proc/self/cmdline` 을 읽는다 | 아니다. `open`/`openat` 트레이스 0건, 바이너리에 그 문자열 없음 |
| `/proc/self/exe` 를 읽는다 | 아니다. `readlink` 트레이스 0건, 바이너리에 그 문자열 없음 |
| `getauxval(AT_EXECFN)` | 아니다. 호출되는 것은 type 16(HWCAP)·26(HWCAP2)·51(MINSIGSTKSZ) 뿐 |
| 우리 로더 옵션이 문제다 | 아니다. **옵션을 하나도 주지 않아도** 동일하게 실패한다 |
| 로더 심링크 이름 | 아니다. 로더를 `echo` 라는 이름의 심링크로 불러도 동일 |
| alr 고유 문제인가 | **그렇다.** 같은 26.04 rootfs 를 proot 로 돌리면 `echo` 가 정상 동작한다 |
| GNU coreutils 로 교체 | 불가. 26.04 의 `coreutils` 는 `all` 아키텍처 전환용 메타패키지이고 실체가 없다 |

추가로 배제한 것: `dl_iterate_phdr`(호출 안 함), 그리고 **Rust 자체**. 게스트의 `rustc` 로 최소 프로브를 만들어 24.04·26.04 양쪽에서 돌려 보니 `std::env::args()`·`args_os()`·`current_exe()` 가 **전부 정확한 값**을 돌려준다. Rust std 는 무관하다.

### 원인: uutils 는 libc 를 우회해 raw syscall 을 발행한다

```
$ llvm-objdump -d .../cargo/bin/coreutils/echo | grep -c '\bsvc\b'
74
$ llvm-objdump -d <일반 Rust 프로브> | grep -c '\bsvc\b'
0
$ llvm-objdump -d <24.04 GNU coreutils ls> | grep -c '\bsvc\b'
0
```

**uutils 바이너리에는 inline `svc` 가 74개 있다.** 일반 Rust 바이너리에도 GNU coreutils 에도 0개다. syscall 번호를 보면 `ioctl`·`fstat`·`fcntl`·`read`·`lseek` 등이 libc 를 거치지 않고 직접 나간다.

이것이 모든 관측을 동시에 설명한다:

- `argv[0]` 이 정확한데도 상관없다 — 이름을 argv 에서 읽지 않는다.
- libc `readlink`/`open` 트레이스가 0건인 것이 맞다 — **libc 를 부르지 않는다.**
- auxv 도 `dl_iterate_phdr` 도 아니다.
- proot 에서는 동작한다 — proot 는 syscall 마다 ptrace 를 걸어 raw syscall 까지 번역한다.

**`LD_PRELOAD` 인터포저는 libc 를 거치는 호출만 볼 수 있다. 이건 고칠 수 있는 버그가 아니라 설계의 경계다** — `docs/00-product.md` §5 가 Go 바이너리에 대해 이미 비목표로 명시한 바로 그 한계이고, Ubuntu 26.04 는 그 성질을 가진 바이너리를 **기본 coreutils 로** 채택했다.

잡으려면 syscall 마다 ptrace 를 걸어야 하는데, 그것이 정확히 PRoot 의 모델이고 그 비용을 내지 않는 것이 이 프로젝트의 존재 이유다([ADR 0001](../adr/0001-signal-only-ptrace-supervisor.md)). 대안인 seccomp user notification 도 불가능하다 — Android zygote 필터가 이미 자리를 차지하고 있고 스택된 필터는 완화될 수 없다([01-platform-facts.md](../01-platform-facts.md) §A2).

## 4. 결정 — 26.04 는 아키텍처가 지원할 수 없다

26.04 는 v1 대상이 아니다(`docs/00-product.md` §2 는 24.04 만 명시한다). 설치가 조용히 반쯤 동작하는 rootfs 를 만들지 않도록 **설치 시점에 경고**한다:

```
alr: WARNING ubuntu-26.04 is not a v1 target.
     Ubuntu 26.04 replaced GNU coreutils with uutils, a Rust
     multicall binary that issues raw syscalls inline instead of
     calling libc.  LD_PRELOAD cannot see those, so ls/cat/echo
     and the rest of coreutils CANNOT work here -- this is the
     same limit documented for Go binaries, not a bug to fix.
     Everything else (bash, apt, dpkg, grep, sed, awk, tar) does
     work.  See docs/RISKS.md.
```

다운로더 일반화와 `cmdline` 합성은 그대로 남긴다 — 둘 다 24.04 에도 이로운 수정이고, 후자는 스펙 요구사항이자 정보 노출 수정이다.

## 5. 절차

M14 는 "이분 탐색이 수렴해도 반대로 한 번 찔러 봐야 한다" 였다. M15 는 그 앞 단계다: **"없다" 는 관측은 계측기가 작동할 때만 증거다.**

그리고 하나 더 — **바이너리를 먼저 볼 수도 있었다.** 동적 관측으로 여섯 개 채널을 배제하는 데 여러 사이클을 썼는데, `objdump -d | grep -c svc` 한 번이면 끝났다. 이 프로젝트는 Go 바이너리에 대해 정확히 그 검사를 문서에 적어 두고 있었다([RISKS](../RISKS.md)). 증상이 "libc 를 거치는 모든 경로에서 안 보인다" 였을 때, 그것 자체가 "libc 를 안 쓴다" 를 가리키는 신호였다.

이번에 `/proc` 접근이 0건이라는 관측을 근거로 한 번 결론을 냈다가, 그 트레이스가 배포되지 않은 빌드에서 나온 값임을 뒤늦게 발견했다(24.04 대조에서 이미 알려진 접근조차 0건으로 나왔다). 계측기를 먼저 검증한 뒤에야 같은 관측이 증거가 되었다. 이 세션에서 "배포본을 확인하라" 는 규칙이 다시 한 번, 이번에는 **측정 도구 자체**에 적용되었다.
