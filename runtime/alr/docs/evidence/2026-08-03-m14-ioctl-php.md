# M14 — `ioctl` §11 구현, 그리고 php 조사가 뒤집은 것

- **날짜**: 2026-08-03
- **기기**: MediaTek arm64, `uid=10297 Seccomp=2 u:r:untrusted_app_27:s0`, 커널 `6.1.145-android14`
- **수용 테스트**: **PASS=76 FAIL=0 KNOWN_FAIL=1** (이전 74/0/2)
- **호환성 폭**: **96/96 설치, 96/96 실행** (이전 95/96)

## 1. `ioctl` §11 — 측정이 스펙의 전제를 반박했다

§11 은 `FIONREAD` 를 "가장 중요" 로 꼽고 **PTY 마스터 쪽 non-blocking read 로 에뮬레이션**하라고 명시한다. 게스트 측은 마스터 fd 를 쥐고 있지 않으므로 그 요구가 이 절 전체를 미구현으로 묶어 두고 있었다.

게스트가 `/dev/ptmx` 로 직접 연 페어에 대해 실측했다(`tests/device/probe_ioctl.c` — script(1)·tmux·expect 가 얻는 것과 같은 경로):

| 허용 | 거부 (EACCES) |
|---|---|
| `TCGETS` `TCSETS` `TIOCGWINSZ` `TIOCSWINSZ` **`FIONREAD`** `TIOCOUTQ` | `TCGETS2` `TIOCGSID` `TIOCGETD` `TIOCEXCL` `TIOCSTI` |

**`FIONREAD` 는 그냥 허용된다.** 에뮬레이션이 필요 없다 — 절 전체를 막고 있던 전제가 틀렸다. (개행 없는 `"abc"` 에 대해 0 을 보고하는 것은 정규 모드 라인 디시플린의 올바른 동작이지 거부가 아니다. `TIOCGPGRP` 의 `ENOTTY` 도 제어 터미널이 아니라서 나는 정상 결과다.)

남은 것은 작고 국소적으로 답할 수 있었다:

- `TCGETS2`/`TCSETS*2` → `TCGETS`/`TCSETS*` 로 번역. 커널 `termios2` 는 커널 `termios` + `{c_ispeed, c_ospeed}` 이므로 앞부분을 그대로 복사하고 속도는 `CBAUD` 비트에서 채운다. **glibc 의 `struct termios` 가 아니라 커널 레이아웃**(NCCS=19)을 써야 한다 — ioctl 은 커널과 직접 대화하므로.
- `TIOCGSID` → `getsid()`
- `TIOCGETD`/`TIOCSETD` → `N_TTY` (pty 에 다른 디시플린은 없다)
- `TIOCEXCL`/`TIOCNXCL`/`TIOCNOTTY` → 0 (이미 배타적으로 소유한 pty 에 대한 권고사항)
- `TIOCSTI` → **계속 EACCES**. `neverallowxperm` 이라 절대 허용될 수 없고, 성공을 가장하면 주입된 입력이 조용히 사라진다.

수정 후 `TCGETS2` `TIOCGSID` `TIOCGETD` `TIOCEXCL` 전부 통과, `TIOCSTI` 만 의도대로 거부. 회귀 테스트 `IOCTL PTY TRANSLATED` / `IOCTL TIOCSTI STAYS DENIED` 추가.

## 2. php — 원인 규명은 실패했고, 그 실패가 결과다

[M11 §5](2026-08-02-m11-breadth.md) 는 php-cli 의 `*** buffer overflow detected ***` 가 **우리 인터포지션 탓이 아님**을 빈 `.so` 대조로 확정하고 근본 원인은 미확인으로 남겼다. 이번에 파고들었다.

**좁혀진 것:**

- 슈퍼바이저가 아니다. 동작하는 `php -h` 와 죽는 `php --version` 의 SIGSYS 프로파일이 **동일**하다(`set_robust_list` 1건).
- 로더가 아니다. `LD_DEBUG=libs` 가 `transferring control` 까지 정상 도달한다. php 의 main 안에서 죽는다.
- glibc 내부다. `__chk_fail` 을 preload 에서 가로채도 **우리 것이 호출되지 않는다** — libc 내부 `_chk` 함수가 자기 안의 hidden alias 를 부른다.
- `php -h` 는 동작하고 `--version`/`-n -r`/인자없음 은 죽는다. 옵션 파싱 이후, 엔진 기동 중이다.

**그리고 여기서 이분 탐색이 무너졌다.** preload 심볼을 그룹으로 빼면서 좁히던 중, 재현성 있는 패턴이 나왔다:

| preload 심볼 수 | php |
|---|---|
| 141 · 146 · 147 · 151 | abort |
| 153 · 155 · 164 · 165 | 정상 |

경계는 152 근처다. 그래서 **php 가 `--version` 에서 쓸 수 없는 심볼**(`scandir`)만 빼는 대조를 돌렸다:

```
scandir 제거 (151 심볼)  →  *** buffer overflow detected ***   (3/3)
```

**특정 심볼이 원인이라는 가설이 반박됐다.** 앞선 이분 탐색 결과 — `__realpath_chk` 아님, `__getcwd_chk` 아님, fstat 계열 아님 — 은 전부 우연이었다. 각 제거가 심볼 테이블 크기를 바꿨을 뿐이다.

**남는 해석**(미확인): Ubuntu 24.04 는 php 를 `_FORTIFY_SOURCE=3` 으로 빌드한다. `=3` 의 검사는 `__builtin_dynamic_object_size` 를 쓰므로 **런타임 할당 크기**에 의존한다. 즉 잠재적 힙 오버런이 있고, preload 의 크기가 기동 시 힙 레이아웃을 흔들어 그것이 검출되는지 여부를 가른다 — 는 가설과 정합한다. 그러나 **검증하지 않았다.**

### 실무적 결론

**출하 빌드(165 심볼)에서 php 는 동작한다.** 호환성 폭이 96/96 실행으로 올라갔다.

> ⚠️ **이것을 "고쳤다" 로 읽지 말 것.** 원인을 모르는 채 임계값 위에 있을 뿐이다. 심볼을 덜어내는 변경은 php 를 다시 깨뜨릴 수 있고, 그때 원인은 그 변경과 아무 관계가 없을 것이다. `tests/device/breadth.sh` 가 php 를 포함하므로 회귀는 잡히지만, **잡힌 뒤에 범인을 오해하기 쉽다** — 이 문단이 그 오해를 막기 위해 있다.

진단용 컴파일 가드를 소스에 남겨 뒀다(`ALR_NO_M13`, `ALR_NO_M13B`, `ALR_NO_FSTAT`, `ALR_NO_SCANDIR`, `ALR_NO_GETCWD_CHK`, `ALR_NO_REALPATH_CHK`, `ALR_DEBUG_CHK`). 다음에 이 문제를 다시 잡을 사람은 이분 탐색을 처음부터 만들 필요가 없다.

## 3. 곁가지로 드러난 것 — 26.04 는 아직 부팅하지 않는다

php 를 런타임과 버전으로 분리하려고 alr 을 proot-distro 의 Ubuntu **26.04** rootfs 에 겨눠 보았다:

```
$ alr run /bin/echo ok
coreutils: unknown program 'ld-linux-aarch64.so'
```

26.04 의 coreutils 는 멀티콜 바이너리라 `argv[0]` 로 디스패치하는데, 우리 `--argv0` 가 반영되지 않는다. **`docs/00-product.md` §2 가 v1 대상으로 잡은 것은 24.04 뿐이므로 목표 미달은 아니지만, 26.04 지원을 주장할 근거는 없다.** 별도 조사가 필요한 항목으로 기록한다 (UNVERIFIED — 원인 미규명).

## 4. 절차

이번 라운드의 교훈은 M12·M13 의 것과 다르다. 그때는 **잘못된 프록시로 측정**했거나 **측정 항목 자체가 없었다**. 이번에는 측정도 프록시도 옳았는데 **인과를 잘못 읽었다** — 여섯 번의 이분 탐색이 전부 일관된 결과를 냈고, 그 일관성이 오히려 잘못된 결론을 뒷받침했다.

무너뜨린 것은 **그럴 리 없는 변수를 넣어 본 대조** 하나였다. 이분 탐색이 수렴할 때, 수렴하는 방향이 말이 되는지 한 번은 반대로 찔러 봐야 한다.
