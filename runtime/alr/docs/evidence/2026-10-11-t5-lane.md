# T5 — tawcroot 레인 통합: Go, codex, busybox가 rootfs를 `/`로 본다

- **날짜**: 2026-10-11
- **엔진 라벨**: `engine=alr` (preload 레인), `engine=tawcroot` (alr-lane, `-DTAWCROOT_ALR` 빌드)
- **기기**: Samsung SM-S937N, Snapdragon 8 Elite SM8750, Android 17 (SDK 37), 커널 6.6.127
- **컨텍스트**: `uid=10057  u:r:untrusted_app_27:s0  Seccomp=2` (Termux sshd를 거친 셸)
- **게스트**: Ubuntu 26.04.1 LTS (glibc 2.43), uutils coreutils, golang-go 1.26.0, codex 0.162.1
- **바이너리**: 릴리스 경로와 같은 빌드다. alr은 NDK 27.2 `--target=aarch64-linux-android29 -static`, alr-lane은 NDK freestanding, preload는 zig 0.16.0이다.
- **결정**: [ADR 0010](../adr/0010-tawcroot-lane.md)
- **목적**: [ADR 0005](../../../../docs/adr/0005-termux-first-goals.md) T5, "Go 바이너리 하나와 codex가 rootfs를 `/`로 보고, 경로 syscall당 추가 비용이 T2 예산 안에 든다"

## 결론

- **T5 기준을 채웠다.** `go build`/`go vet`/빌드된 Go 바이너리, codex, busybox-static이 rootfs를 `/`로 본다.
- **수용 테스트**: `PASS=187 FAIL=0 KNOWN_FAIL=1 SKIP=0`([원본](2026-10-11-t5-lane-acceptance.txt)). 레인 검사 15개가 이 안에 있다.
- **호환성 폭**: `96/96`([원본](2026-10-11-t5-lane-breadth.txt)).
- **슈퍼바이저 스위트**: 13/13.
- **T2 워크로드는 모두 1.2배 이내**다([원본](2026-10-11-t5-lane-t2.txt)). 레인에서 도는 Go 워크로드는 1.01~1.02배이고, `alr run`의 최상위 실행은 alr을 정적 링크한 뒤 네이티브보다 빠르다.
- 이 증거 시점에는 경로 syscall만 반복하는 마이크로 워크로드가 예산을 넘었다. busybox `find`는 1.34배, `ls -lR`은 1.65배였다. 남은 비용의 구성은 §5에 있다. 그 뒤의 변경으로 1.08배와 1.09배가 되었다([후속 증거](2026-10-11-t5-lane-cost.md)).

## 1. 레인 통합

ADR 0010의 결정대로 넣었다.

| 위치 | 동작 |
|---|---|
| `alr run`(최상위) | 대상이 정적 ELF이거나 `Go` 노트가 있는 동적 ELF이면, 슈퍼바이저 없이 `alr-lane -r ROOT -b /proc:/proc -b /dev:/dev -b /sys:/sys -- 게스트경로 인자...`로 exec한다. 환경은 게스트 형태에서 `LD_*`, `ALR_*`, `LOCPATH`를 뺀 것이다 |
| preload의 execve | 같은 판정으로 레인에 넘긴다. 게스트 경로 인자를 바꾸지 않는다 |
| 슈퍼바이저 | `PTRACE_EVENT_EXEC`에서 `/proc/<tid>/exe`가 alr-lane이면 `PTRACE_DETACH`한다. 떼어 낸 리더의 종료 상태도 기다린다 |
| 끄기 | `ALR_LANE=0`이면 이전 동작이다 |

기기 결과:

```
alr run /usr/bin/go version                 go version go1.26.0 linux/arm64      (레인, 경고 없음)
alr run /bin/bash -c 'go build -o gh . && ./gh'
                                            hi localhost true true <nil>          (os-release 읽기, DNS 모두 성공)
alr run /bin/busybox sh -c 'cat /etc/os-release | head -1; pwd; id'
                                            PRETTY_NAME="Ubuntu 26.04.1 LTS"  /root  uid=10057(alr)
alr run /usr/local/bin/codex doctor         git /usr/bin/git, search /usr/bin/rg  (rootfs 안의 도구)
```

통합하기 전에는 `go build`가 `mkdir /tmp/go-build…: permission denied`로 실패했다([T5 uutils 증거](2026-10-11-t5-uutils-preload.md) §남은 것).

## 2. 통합 중에 찾아 고친 결함

| 결함 | 증상 | 수정 |
|---|---|---|
| Go 노트 판별 | cgo 바이너리(`go build`의 기본값)가 레인으로 가지 않았다. 레인 밖에서 Android의 `/etc`를 읽었고, DNS는 `[::1]:53`으로 갔다 | cmd/link는 노트 이름을 `"Go\0\0"`(namesz 4)로 쓴다. 판별 코드는 3만 받았다. 둘 다 받도록 고쳤고, `tests/host/test_exec_rule.c`에 실제 형태를 넣었다 |
| 정규화하지 않은 루트 경로 | `ALR_ROOT_DIR=$HOME/../usr/...`로 실행하면 `getcwd`가 호스트 경로를 돌려줬다. uutils도 `unknown program 'ld-linux-aarch64.so'`로 실패했다(수용 44 FAIL) | 커널이 돌려주는 경로(`getcwd`, `/proc/self/fd`, `AT_EXECFN`)는 모두 정규형이다. 루트 경로를 `realpath`로 정규화했다. 검사 `CLI ROOT DIR CANONICALIZED`를 추가했다 |
| 레인이 만든 하드링크 | `ln h1 h2`가 `h2 -> tawcroot:link:861420` 심링크를 만들었다. preload 레인에서는 `No such file`이었다 | 하드링크가 거부되면 preload처럼 복사한다. link store를 끈다 |
| 레인이 만든 절대 심링크 | `ln -s /etc/os-release abs`가 절대 대상을 그대로 저장했다. preload 레인에서는 Android의 `/etc`를 가리켰다 | preload처럼 링크의 부모 깊이로 상대화한다(`../../../etc/os-release`) |
| 레인의 신원 | 레인은 항상 uid 0이었고 stat도 root 소유로 보였다. preload는 실제 uid다 | 실제 uid/gid로 시작하고 stat을 꾸미지 않는다. `ALR_FAKEROOT=1`이면 `--fakeroot`로 이전 동작이다 |

## 3. alr을 정적 링크한다

T2를 다시 재는 중에 `git status`(최상위)가 1.18~1.24배로 나왔다. 기준 커밋(18515e4)의 alr도 같은 값이어서 이번 변경으로 생긴 회귀는 아니었다. 게스트 셸 안의 git 한 번은 약 17 ms인데 `alr run`으로는 26 ms였다. 그 차이의 대부분은 alr 자신의 시작 비용이었다.

같은 소스를 NDK로 동적·정적 두 가지로 빌드해 번갈아 쟀다(hyperfine `-N`, 30회, 중앙값 ms, 4회차).

| 명령 | 네이티브 | 동적 alr | 정적 alr |
|---|---:|---:|---:|
| `git -C repo status`, 파일 1만 개 | 21.3~22.3 | 25.8~27.0 | 18.7~19.4 |
| `python3 -c pass` | 22.6~23.3 | 24.2~29.0 | 16.1~17.5 |

- 동적 alr은 main에 들어가기 전에 syscall 1,111개를 낸다. 정적 alr은 277개다. 동적 쪽은 링커 설정(`/linkerconfig/ld.config.txt`, APEX 네임스페이스), libtermux-exec, 그리고 libc 초기화가 dlopen하는 `libnetd_client.so`와 그 의존성(`libc++.so`, `libm.so`)을 거친다.
- 빈 `main`만 있는 프로그램은 동적과 정적의 차이가 1~1.5 ms였다. 그래서 나머지 차이가 어디서 오는지는 확인하지 못했다. 큰 주소 공간을 가진 부모의 fork와 ptrace 비용이 유력한 후보다.
- `LD_PRELOAD`(libtermux-exec)를 뺀 실행에서도 동적 alr은 25~28 ms였다. 그러므로 원인은 libtermux-exec가 아니다.

**정적 bionic에는 걸림돌이 둘 있었다.**

1. API 24의 `libc.a`로 링크한 정적 arm64 실행 파일은 시작할 때 중단된다. 오류는 `executable's TLS segment is underaligned: alignment is 8, needs to be at least 64`이다. 그래서 alr만 API 29로 빌드한다. alr-doctor는 진단 도구라 동적 API 24로 둔다.
2. 정적 libc의 `getaddrinfo`는 netd에 닿지 못한다. 위 dlopen이 없어서 `/etc/resolv.conf`로 넘어가는데, Android에는 그 파일이 없다. 그래서 `getent hosts github.com`이 rc=2로 실패했다. 이를 고치려고 resolvd가 `/dev/socket/dnsproxyd`에 직접 질의한다. bionic의 `android_getaddrinfo_proxy`가 보내는 것과 같은 텍스트 명령을 보내고 같은 응답을 해석한다. 숫자 주소와 이름 없는 질의는 지금처럼 libc가 처리한다. 질의 결과는 동적 빌드와 같았다(`getent ahosts example.com` 출력 diff 없음). Private DNS와 VPN을 따르는 성질도 그대로다. netd가 해석하기 때문이다.

## 5. 레인 자체의 비용

같은 busybox 바이너리를 레인과 `ALR_LANE=0`(가상화 없음, 경로 인자만 호스트 형태)으로 비교했다. 트리는 `/usr/share`이고 파일은 61,865개다.

| 단계 | `find -type f` | `ls -lR` |
|---|---:|---:|
| 기준 (`ALR_LANE=0`) | 274 ms | 338~348 ms |
| 통합 직후 | 609 ms (2.22배) | 1,049 ms (3.05배) |
| 아래 변경 후 | 367 ms (1.34배) | 576 ms (1.65배) |

strace로 센 트랩 하나(`rt_sigreturn` 하나)마다 따라붙는 syscall과, 그것을 없앤 변경은 다음과 같다(`find /usr/share/doc`).

| 따라붙는 syscall | 통합 직후 | 변경 후 | 변경 |
|---|---:|---:|---|
| `gettid` | 2.6 | 0 | 게스트 메모리 복사는 tgid를 `MADV_WIPEONFORK` 페이지에 캐시한다. 실제 uid일 때는 rescue 슬롯을 잡지 않는다 |
| `readlinkat` | 2.3 | 0.44 | 심링크가 아님을 확인한 디렉터리 경로를 캐시한다. 이 프로세스가 rename, unlink, symlink, chroot를 하면 비운다 |
| `process_vm_writev` | stat마다 1 | 0 | 실제 uid일 때는 커널이 게스트의 stat 버퍼에 직접 쓴다 |
| `process_vm_readv` | 경로마다 1 | 경로마다 1 | 남았다 |

같은 기기에서 잰 단가는 다음과 같다(20만 회 평균).

| 호출 | ns |
|---|---:|
| `process_vm_readv` 256 B | 318~437 |
| `fstatat` | 403~413 |
| `readlinkat` (EINVAL) | 303~314 |
| `getppid` | 123~124 |
| 레인 트랩 왕복 ([S2](2026-10-11-s2-ret-trap-cost.md)) | 약 400~900 |

남은 비용은 경로가 있는 트랩마다 시그널 왕복과 게스트 경로를 읽는 `process_vm_readv` 한 번이다. 경로 syscall 하나의 원가와 비슷한 크기다. 이것을 없애려면 게스트 메모리를 직접 읽고, 잘못된 포인터는 SIGSEGV 핸들러에서 EFAULT로 돌려야 한다. 그러려면 tawcroot가 게스트의 SIGSEGV를 가로채고 다시 전달해야 한다. Go와 JVM이 SIGSEGV에 의존하므로, 이 작업은 따로 결정한다. 이 작업은 [후속 증거](2026-10-11-t5-lane-cost.md)와 [ADR 0010](../adr/0010-tawcroot-lane.md) 결정 7에서 했다.

## 정직한 한계

- Snapdragon 한 대, Android 17에서만 쟀다. 이 기기는 짧은 측정에서 변동이 크다(같은 `true`가 7~22 ms). 그래서 모든 비교는 같은 hyperfine 실행 안에서 번갈아 잰 중앙값이다.
- 디렉터리 캐시는 다른 프로세스가 디렉터리를 심링크로 바꾼 것을 보지 못한다. 그때는 커널이 그 심링크를 따라간다. alr의 rootfs에는 상대 심링크만 있다. 설치할 때 상대화하고, 두 레인이 새로 만드는 심링크도 상대화한다. 그래서 그 결과도 rootfs 안에 머문다. 이것은 preload 레인이 늘 기대고 있는 것과 같은 해석이다. 이 경우를 재현하는 테스트는 만들지 않았다.
- 레인의 하드링크는 복사다. 한 이름으로 쓴 내용은 다른 이름에 보이지 않는다. preload 레인의 동작과 같다.
- dnsproxyd 프로토콜은 Android의 내부 인터페이스다. Android 17에서 확인했다. 연결이 안 되면 libc로 돌아간다. 정적 alr에서는 그 경우 DNS가 실패한다.
- 정적 alr을 Termux 패키지 레시피로 빌드할 수 있는지는 termux-packages에서 확인하지 않았다(레시피에 UNVERIFIED로 적었다).
